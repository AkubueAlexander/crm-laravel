Multi-Tenant CRM/ERP — Full Platform Blueprint (React + TypeScript / Laravel API) Laravel 13 (API-only) + PostgreSQL + Reverb — React 18 + TypeScript + Vite (decoupled SPA), TanStack Query, TanStack Table, TanStack Router (or React Router), React Hook Form + Zod, Zustand, Tailwind CSS, Laravel Sanctum (SPA auth), Laravel Echo Architecture decision, stated once up front: Laravel is a pure JSON API (no Blade, no Inertia, no server-rendered views). React is a fully decoupled SPA, same-origin with the API, authenticated via Sanctum's cookie-based SPA flow (not a Bearer-token mobile flow — same-origin means CSRF protection stays simple and you avoid token-storage tradeoffs entirely). The two apps deploy as one artifact for simplicity (Laravel serves the built Vite bundle from public/), but the seam between them is a real, versionable JSON contract — not an implementation detail. That seam is what lets 12.4's QuickBooks sync, 13.4's HRIS integration, and 9.8's public lead-form endpoint all be first-class API consumers instead of special cases. 0.0 Stack & Project Setup Backend (Laravel 13, API-only): PHP 8.5, routes/api.php only — no web routes beyond Sanctum's CSRF cookie endpoint and the Fortify API actions. Modular monolith folder layout unchanged from the original: app/Domain/<Feature> for framework-agnostic business logic, but app/Http/Controllers/Api/<Feature> + app/Http/Resources/<Feature> replace app/Livewire/<Feature> as the presentation layer. PostgreSQL 16. Redis-backed queues. Laravel Reverb for broadcasting. Laravel Sanctum for SPA session auth (stateful domains configured to the SPA's origin). API responses are versioned under /api/v1/... from day one — cheap now, expensive to retrofit once 12.4/13.4-style external consumers exist. Frontend (React 18 + TypeScript, Vite): Routing: TanStack Router (file-based, fully typed route params/search — worth it over React Router given how many tenant/board/deal IDs flow through URLs in this app) or React Router v6 if the team prefers its maturity. Server state: TanStack Query for every piece of data that originates from the API — deals, contacts, forecasts, invoices, inventory, everything in sections 3–13. Nothing fetched from the API is ever duplicated into Context or Zustand. Client/UI state: Zustand, small and deliberately boring — active Kanban filter chips, sidebar collapsed/expanded, active theme, "which modal is open." If a piece of state could be derived from an API response, it doesn't belong in Zustand. Forms: React Hook Form + Zod for every mutating form — deal creation, contact/lead forms, Quote/Invoice line-item builders, Segment/Campaign builders, tenant settings. One Zod schema per form, ideally generated from (or kept in lockstep with) the Laravel Form Request rules it mirrors — the Zod schema is a UX layer, not the security boundary; the Laravel Form Request remains that boundary (same non-negotiable point as the original's 2.6). Tables/grids: TanStack Table (headless) for every data grid — Contacts, Invoices, Purchase Orders, the GL report, the audit log viewer. Column defs are typed, sorting/pagination/column-visibility are table-state, but row data still comes from TanStack Query — the two libraries compose, they don't overlap. Real-time: laravel-echo + pusher-js (Reverb is protocol-compatible) wrapped in a small useEchoChannel hook (6.0) that calls queryClient.invalidateQueries(...) (or a targeted setQueryData patch) on incoming events, rather than managing a parallel copy of the data in component state. Drag/drop (Kanban): dnd-kit — headless, accessible, and (unlike Alpine's manual drag handlers in the Livewire version) has first-class React primitives for sortable lists, which the Pipeline Board (3.0/8.1) needs. Charts: Recharts, for Forecast Dashboard (4.0) and Campaign Dashboard (9.10). Styling: Tailwind CSS v4, shared config with the backend's asset pipeline if you want a single npm workspace root. Project layout: /app Laravel API (Domain/, Http/Controllers/Api/, Http/Resources/) /frontend /src /features/<domain> vertical slices: deals, contacts, forecasting, marketing, sales, inventory, accounting, hr /api TanStack Query hooks (useDeals, useDeal, useMoveDealStage, ...) /components presentational + container components /schemas Zod schemas + inferred TS types /shared /components Button, Table primitives, Modal, etc. /hooks useEchoChannel, usePermission, useTenant /stores Zustand stores (ui.ts, filters.ts) /lib apiClient (typed fetch/axios wrapper), queryClient config

Each features/<domain> folder mirrors a Laravel Domain/<Feature> folder one-to-one — the vertical-slice intent from the original blueprint survives the framework swap unchanged. Tooling: Pint + Larastan on the backend as before. ESLint (typescript-eslint) + Prettier on the frontend, tsc --noEmit in CI as the type-check gate. Zod schemas act as the runtime validation layer TypeScript's compile-time types can't provide on their own (an API response can lie to tsc; it can't lie to a Zod .parse()). 1.0 Multi-Tenancy Foundation Backend enforcement is unchanged from the original — shared DB, tenant_id discriminator, Eloquent global scopes, ResolveTenant middleware, composite indexes, the TenantGuard save-time defense-in-depth. None of that logic moves or weakens by going decoupled; if anything, a real API forces you to be more disciplined about it, because there's no server-rendered view accidentally leaking a cross-tenant relationship into a Blade partial — every response is an explicit, reviewable API Resource. What changes is how the frontend knows which tenant it's operating as, since there's no server-side session driving a Blade layout anymore: 1.1 On login, the API returns the authenticated user's tenant context (id, name, branding) as part of the auth payload; React stores it in a small useTenant hook backed by TanStack Query's cache (['auth', 'me']), not Zustand — it's server-derived data, so it follows the "server state lives in TQ" rule even though it barely ever refetches. 1.2 Query-key tenant namespacing is the frontend's actual isolation discipline: every TanStack Query key that touches tenant-scoped data is prefixed with the tenant id — ['deals', tenantId, boardId], ['contacts', tenantId, ...]. This isn't a security control (the backend's global scope is the real control) but it prevents a nasty class of bug where a stale cache entry from tenant A briefly renders under tenant B during a session/impersonation switch, and it's essentially free to add. 1.3 The API never trusts a tenant_id sent from the client in a request body — every mutating endpoint re-derives tenant context from the authenticated session server-side (identical in spirit to the original's "claims-equivalent" point in 2.4, just phrased for a stateless API instead of a session-baked Livewire request). 1.4 If you ever support a user belonging to multiple tenants (multi-org membership, flagged as cheap-to-build-now in the original's 2.1), the frontend needs an explicit tenant switcher that (a) clears/re-namespaces the TanStack Query cache on switch — queryClient.clear() or a full queryClient.invalidateQueries() scoped to the old tenant id — and (b) re-issues the Sanctum session check, since the switch is itself a privileged server-side action, not a client-side dropdown that just changes a header. 1.5 Reverb/Echo private-channel auth (unchanged from the original's 6.1/1.7 note): the channel-authorization callback in routes/channels.php re-verifies tenant membership at socket-subscribe time, since that's the one auth path that doesn't run through the normal request middleware stack — true whether the frontend is Blade/Livewire or React, since it's a property of how WebSocket auth works, not of the UI framework. 2.0 Identity, Auth & RBAC Backend: Laravel Sanctum (SPA mode — cookie-based, CSRF-protected, same-origin) replaces the Fortify-wired-into-Livewire-components approach; Fortify's underlying actions (login, register, password reset, 2FA) are reused, just invoked via routes/api.php actions that return JSON instead of redirecting a Blade/Livewire view. spatie/laravel-permission with tenant-scoped teams is unchanged. 2.1 Auth flow: React login/register forms (RHF + Zod) first GET /sanctum/csrf-cookie, then POST /login with credentials; on success, a useCurrentUser TanStack Query hook (['auth', 'me']) fetches the authenticated user + permissions + tenant context in one call and becomes the source of truth for "is anyone logged in" — there's no separate global auth Context duplicating what the query cache already holds. 2.2 Protected routes: a <RequireAuth> wrapper component reads the useCurrentUser query's status (loading/error/success) and redirects to /login on a 401, rather than a custom auth-state machine — TanStack Query's own status enum (pending/error/success) already models exactly the states a route guard needs. 2.3 Permissions: the API returns the user's resolved permission set (from Spatie's teams-mode roles) as part of the /me payload; a usePermission('deals.transition') hook reads it out of the cached query rather than re-deriving anything client-side. Every permission check is duplicated server-side in the corresponding Action/policy — the frontend hook only ever controls what's shown, never what's allowed, same non-negotiable rule as the original's 2.6 ("a hidden button is not a security boundary"), just enforced via a hook instead of a Blade @can directive. 2.4 Server-side re-validation inside every Action/Job stays identical to the original — this is a backend-layer guarantee that doesn't change no matter what's rendering the button. 2.5 2FA / invite flows: signed-URL invite acceptance (8c.2) becomes a React route that reads a token from the URL, calls the corresponding Fortify-backed API action, and redirects into the app on success — same flow as before, just JSON in/out instead of a Blade form post. 3.0 Deals & Pipeline State Machine Backend state machine (Spatie's laravel-model-states, Deal::transitionTo(), DealStageChanged event, deal_stage_audit_log, optimistic-concurrency lock_version column) is entirely unchanged — this was already framework-agnostic domain logic in the original blueprint, and going decoupled doesn't touch it. 3.1 POST /api/v1/deals/{deal}/transition — the one mutation endpoint, mirroring the original's single-entry-point principle (3.3); accepts { to_stage, lock_version }, returns the updated DealResource or a 409 with the current server-side state on a version mismatch. 3.2 Frontend mutation: useMoveDealStage() (TanStack Query useMutation) with an optimistic update — immediately patch the dragged card into its new column via queryClient.setQueryData, then reconcile against the real response. On a 409 (someone else moved it first — the concurrency case from the original's 3.7), roll back the optimistic patch and surface "this deal was updated by someone else — refresh to see the latest stage," the same UX the original specified, just implemented as a TQ onError rollback instead of a Livewire flash message. 3.3 Kanban board (Deals/Board): dnd-kit's sortable primitives for drag between stage columns; on drop, calls the mutation from 3.2 rather than mutating local board state directly — the board's rendered state is always derived from the TanStack Query cache for that board's deals, never a separate useState copy that could drift from it. 3.4 Live updates: DealStageChanged broadcasts over the tenant+board-scoped private channel exactly as in the original's 6.0; a useEchoChannel hook listening on that channel calls queryClient.setQueryData (or a scoped invalidateQueries) to patch just the affected card — functionally identical to the original's "patch only the affected card" goal, achieved through TanStack Query's cache instead of a targeted Livewire re-render. 3.5 Deal creation/edit form: RHF + Zod — this is a good early example of why RHF matters here specifically: the deal form has conditional fields (e.g. expected_close_date required unless stage is Won/Lost) that Zod's .refine()/.superRefine() expresses cleanly, and RHF's uncontrolled inputs mean the value field's keystrokes don't re-render the rest of the form (or, worse, the whole board if the form lives in a modal over it). 3.6 Audit log (deal_stage_audit_log) is surfaced via a TanStack Table-driven list in the Deal detail view — read-only, paginated, sortable by date/actor. 4.0 Forecasting Engine Unchanged on the backend — plain PHP classes in app/Domain/Forecasting, no framework dependency, fully Pest-testable, exactly as in the original. 4.1 GET /api/v1/forecast?tenant_id=... (tenant implicit from session) returns commit-vs-best-case DTOs. 4.2 useForecast() TanStack Query hook, keyed ['forecast', tenantId], feeding Forecasting/Dashboard — a Recharts bar/line combo replacing the original's Chart.js-via-Alpine approach, since Recharts is a proper React-native charting library rather than an imperative library bolted on through Alpine's escape hatch. 4.3 Per-tenant pipeline settings (stage probabilities) editable via an RHF+Zod form in the Admin surface (8c.1); a useUpdatePipelineSettings mutation invalidates the ['forecast', tenantId] query on success so the dashboard reflects new probabilities immediately. 5.0 Contacts & Fuzzy Matching Backend unchanged — PostgreSQL, pg_trgm GIN index, two-stage trigram-then-PHP-scoring DuplicateDetectionService, exactly as the original's 5.0. 5.1 POST /api/v1/contacts/check-duplicates — a lightweight endpoint the Contact form calls on blur/debounce (not on every keystroke) via a useDuplicateCheck mutation, surfacing a DuplicateWarning component inline in the RHF form without blocking submission — same UX intent as the original's 5.4. 5.2 Contacts list (Contacts/ContactList) is a TanStack Table instance: server-side pagination and sorting (the table's manualPagination/manualSorting flags, since with tenant-scale data you want the API doing the LIMIT/ORDER BY, not the client sorting a fully-fetched dataset), backed by a useContacts({ page, sort, filters }) TanStack Query hook whose query key includes the pagination/sort state — TQ's caching means flipping back to a previously-viewed page is instant, no refetch. 5.3 Per-tenant match-threshold config (5.5 in the original) is a simple settings form, same pattern as 4.3. 6.0 Real-Time Layer — Laravel Reverb + Laravel Echo (React) Server-side broadcasting (private tenant+board channels, ShouldBroadcast events, channel-auth callback re-verifying tenant membership) is identical to the original's 6.0 — this is backend infrastructure that doesn't know or care what's consuming it. 6.1 useEchoChannel hook — the one piece of real glue code this section needs: function useEchoChannel(channel: string, event: string, onEvent: (payload: unknown) => void) { useEffect(() => { const sub = echo.private(channel).listen(event, onEvent); return () => { echo.leave(channel); }; }, [channel, event]); }

Used as useEchoChannel(tenant.${tenantId}.board.${boardId}, 'DealStageChanged', (payload) => queryClient.setQueryData(...)) — this is the direct replacement for the original's Echo.private(...).listen(...) call inside a Livewire component's wire:init, just living in a useEffect with a cleanup function instead of Livewire's dehydrate lifecycle. 6.2 Unsubscribe on unmount is the effect's cleanup function — React's useEffect cleanup is a closer, more predictable match for "unsubscribe on teardown" than the original's wire:navigate-triggered Echo.leave(), since it fires deterministically on component unmount rather than depending on Livewire's SPA-navigation lifecycle. 6.3 Reconnection: Echo/Pusher-protocol's auto-reconnect and Reverb's re-authorization on reconnect behave identically regardless of frontend framework; the integration test from the original's 15.4 (two authenticated clients, one moves a deal, assert tenant-scoped delivery) is unchanged and just as necessary here. 6.4 Notifications' live bell-icon push (8b.2) uses the same hook against a per-user private channel, invalidating a ['notifications', userId] query on receipt. 7.0 Data Layer & Persistence Entirely backend, entirely unchanged — Eloquent models per feature folder, BelongsToTenant trait, soft-delete/tenant-scope interaction caveat, migration strategy, TenantSeeder. A decoupled API doesn't touch this layer at all; it's worth restating (as the original did for its own non-issue in 7.2) that this section simply has no React-side analogue. New, decoupling-specific addition: every Eloquent model that gets exposed over the API needs a corresponding API Resource (app/Http/Resources/<Feature>) that explicitly whitelists the fields sent to the client — this is the boundary that prevents an accidental $model->toJson() from leaking a column (e.g. an internal lock_version, a soft-deleted-but-not-yet-purged row's data, or another tenant's FK id sitting unused on a model) that a Blade view would never have rendered but a naive API serializer might. Pair each Resource with a matching Zod schema on the frontend (features/<domain>/schemas) so a shape mismatch fails loudly in development (a Zod .parse() throw) instead of silently rendering undefined in production. 8.0 React Component Architecture — Vertical Slices This section replaces the original's Livewire UI section (8.0) and its Alpine-scoping section (8d.0) entirely — there's no Livewire/Alpine coexistence tension in a pure React app, because there's only one client-side reactivity model to reason about. The corresponding discipline that does still matter is not conflating server state with UI state, which is the direct successor to the original's "Alpine only touches subtrees with no tenant data" rule: 8.1 State-placement rule (the practical replacement for 8d.0's Alpine-scoping rule): Data that came from the API → TanStack Query, always, never copied into useState "just to make a component simpler." If a component needs derived/filtered data, derive it in a useMemo off the query's data, don't clone it into local state that can drift. Ephemeral, purely-visual state (is this dropdown open, is this modal visible, which tab is active) → plain useState local to the component, or lifted one level if a sibling needs it — this is the React equivalent of the original's "approved Alpine use cases" (8d.1): dropdown/menu state, modal visibility, toast timers, filter-chip visual toggle. Cross-cutting UI state that needs to persist across route changes or be read by unrelated components (sidebar collapsed, active theme, which Kanban filters are active) → Zustand, small and typed. The graduation rule from the original's 8d.2 still applies almost verbatim: if a "simple toggle" needs to affect anything persisted or tenant-scoped, it graduates to a TanStack Query mutation through the proper Action/permission pipeline (2.3) — it does not stay in local useState with a manual fetch() bypassing the typed API client and its auth/error handling. 8.2 Component structure per feature: a container component owns the TanStack Query hooks and mutations and passes plain props down; presentational components underneath are prop-driven and easy to test/story in isolation — the same "component owns data, children just render it" discipline the original achieved implicitly through Livewire's component boundaries, made explicit here since React doesn't enforce it for you. 8.3 Forms Frontend-side, pair it with a browser error-reporting tool (Sentry or similar) tagged with the same tenant_id/user_id so a cross-tenant debugging session can correlate a frontend exception with the corresponding backend log line. 14.2 Validation exists in two layers on purpose: Zod on the frontend (fast feedback, no round-trip for obviously-invalid input) and Laravel Form Requests on the backend (the actual boundary). They should assert the same rules where possible, but the backend rule is the one that's load-bearing — a Zod schema is UX, not security, worth restating here since it's the most common mistake teams make when adding client-side validation to what used to be a purely server-validated Livewire form. 14.3 Global exception handling: the backend maps domain exceptions to structured JSON error responses (a consistent { message, errors, code } shape) via bootstrap/app.php's withExceptions(), exactly as the original specified — just returning JSON instead of a Livewire-flashed error. The frontend's TanStack Query onError handlers and a root Error Boundary are what actually display those errors; the two layers compose into the same "domain exception → user-friendly message" pipeline the original had, just split cleanly across the API boundary instead of living entirely server-side. 14.4 Rate limiting on the public lead-form endpoint (9.8) and Reverb reconnect storms — unchanged, backend-only, and arguably more important now that 9.8 is explicitly reachable by a client the main SPA's auth layer never sees. 15.0 Testing Strategy 15.1 Backend unit tests (Pest): unchanged — DealState transitions, ForecastingEngine, DuplicateDetectionService, LeadScore, no DB, no UI. 15.2 Backend feature tests (Pest + real Postgres): unchanged, including the load-bearing tenant-isolation test — this test matters more, not less, now that it's the API's job alone to enforce isolation with no server-rendered-view fallback catching a mistake. 15.3 Frontend unit/component tests: Vitest + React Testing Library, the direct replacement for the original's Livewire::test(...) component tests — render Deals/Board, Sales/QuoteBuilder, Marketing/CampaignDashboard with MSW (Mock Service Worker) intercepting the API calls, asserting render output and interaction side effects (a drag on the Kanban board triggers the expected mutation call; a Zod validation error renders under the right field) without needing a real backend running. 15.4 API contract tests: a lightweight layer worth adding specifically because the API is now a real, versioned contract rather than an implementation detail — either OpenAPI-schema-generated TypeScript types checked against actual responses in CI, or a Pest test suite asserting each API Resource's shape matches what the frontend's Zod schemas expect. This is new relative to the original blueprint and is the direct cost of decoupling: nothing catches a Resource/Zod-schema drift for you automatically the way a shared Blade template implicitly did. 15.5 Reverb/broadcast integration test: unchanged from the original's 15.4 — two simulated authenticated clients, one moves a deal, assert tenant-scoped delivery — plus, on the frontend side, a component test asserting the useEchoChannel hook correctly patches TanStack Query's cache on a mocked incoming event. 15.6 End-to-end: Playwright driving the real built SPA against a real (test) Laravel API — the Kanban drag-and-drop, the Quote builder's multi-line-item flow, and the full Lead→Deal conversion path are the highest-value E2E candidates, since they're the flows most likely to have a subtle break at exactly the API-contract seam this architecture introduces. 16.0 Deployment & DevOps 16.1 Single-artifact deploy, still monolithic: npm run build produces a static Vite bundle that Laravel serves from public/ (or a CDN in front of it) — one deploy pipeline, one container/server, same "monolith" property the original blueprint valued, even though the API/SPA boundary inside it is now explicit. This is the resolution to the earlier "is API worse than tightly coupled" question in practice: decoupled contract, coupled deployment. 16.2 Local dev: docker-compose.yml — Laravel app + Postgres + Redis + Reverb + Mailpit (unchanged from the original), plus the Vite dev server running alongside with its proxy pointed at the Laravel API for same-origin cookie behavior in development (Vite's server.proxy config, so Sanctum's CSRF cookie flow works identically to production without CORS workarounds). 16.3 CI pipeline: Pint/Larastan + Pest on the backend (unchanged); ESLint + tsc --noEmit + Vitest on the frontend; the API-contract test from 15.4 as a required check that gates merges on both sides of the seam; Playwright E2E as a pre-deploy gate. 16.4 Reverb at scale: unchanged from the original — Reverb scales as its own service with Redis as the pub/sub backplane; nothing about a React frontend changes Reverb's own scaling story, since it was always designed to be deployed independently of whatever's rendering the UI. 16.5 Sanctum SPA-mode specifics worth calling out for deployment: the SANCTUM_STATEFUL_DOMAINS and session-cookie domain config need to match the actual production origin exactly (including port/subdomain), and this is the one genuinely new deployment-config surface that a tightly-coupled Blade/Livewire or Inertia app wouldn't have needed to think about at all — worth a deployment-checklist line item so it isn't discovered the hard way in a staging environment with a different subdomain than prod.
